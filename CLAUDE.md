# omnicore-example-users

Sandbox + reference consumer of the [OmniCore](../omnicore/CLAUDE.md) framework. Two purposes: a **test bench** to exercise framework features and surface gaps, and a **canonical example** of assembling a microservice with OmniCore. It is a sandbox — not production; keep it simple.

Implements a users CRUD with addresses as a child aggregate (POST, PUT strict, PATCH partial, PATCH `/:id/archive` + `/unarchive` aggregate-aware, DELETE hard, GET by id, GET by params), plus a second role — **Employee** (`/employees/*`, 100% canonical, no by-id route) — over the SAME shared Person identity, exercising the SharedBase paths one role cannot: base reuse/refcount across roles, two role-owned child collections (`Dependent` + `JobHistory`), a role sibling (`employee_bank_accounts`) and a CHILD-level sibling (`dependent_health_plans`). A READ-ONLY **Persons** surface (`/persons`, `/persons/:id`, exports, GraphQL `persons`) serves the all-in-one identity projection — the `SharedBaseView` over the Person base, one document per identity with a sub-object per role; a person is written through its roles. Also a `ShowcaseFeature` of framework-exercise routes (`/whoami`, `/showcase/keycloak/*`, `/showcase/httpclient/*`, `/showcase/cache/*`, `/echo/*`) and a parallel **manual showcase** under `/showcase/users-custom/*` that hand-rolls every layer above `domain/` for the users aggregate.

## Working rules

Condensed; the full reasoning lives in [`../omnicore/CLAUDE.md`](../omnicore/CLAUDE.md).

1. **Framework changes need explicit maintainer approval.** A finding here → STOP, document it (files+lines), propose (framework fix vs local workaround), wait. No local workaround without approval either — the fix-vs-workaround call is the maintainer's.
2. **The `qa/` suites are an oracle, not editable to pass.** A failing case is a signal — investigate the real cause, report, wait for approval before touching any expectation/fixture. Adding new cases for new behavior is fine and expected.
3. **Unit-test every change.** Wrap up a round with green `go build -tags 'postgres nats' ./... && go vet -tags 'postgres nats' ./... && go test -tags 'postgres nats' ./... -count=1` (this service's dialect is postgres; `nats` links the message-transport adapter — a transport tag is mandatory, like the engine tag). Then ask via `AskUserQuestion` whether to also run the E2E suites — recommend the relevant subset, always offer "run all".
4. **Verify, never guess** — back every claim about the code with a `Read`/`grep`, including while planning.
5. **English everywhere** except the seven translation catalogs in `internal/application/translations/` (`ptbr`/`eng`/`esp`/`fra`/`deu`/`ita`/`nld`).
6. **The AI never writes git history.** Get onto a coherent branch at task start (`feature|fix|docs|refactor/<slug>` via `git checkout -b` off `main`, or `git branch -m` to rename an in-flight branch); apply edits; deliver one English commit-message suggestion as chat text. No commit/push/tag/PR/release.
7. **This file is current state, not history** — no "Phase N", no changelog/dated entries, no references to removed APIs.

## Layout

Standard DDD layers consuming the framework. The four layers live under `internal/` (Go's compiler-enforced "private to this module" root — everything in this repo imports them freely, no other module can); the published gRPC contract lives beside it in `proto/`:

- `internal/domain/` — `User` + `Employee` (`AggregateRoot`s over the same Person identity), the root-only notifications + the manual-showcase repository port. Pure, zero IO. Two subpackages hold the reused pieces (each with its own `notifications.go`, since `domain` imports them — a notification declared there would cycle): `internal/domain/vos/` — the **value objects** (raw: `Name`/`Email`/`Phone`/`Document`/`ZipCode`/`HealthPlanCard`; enum: `Ethnicity`/`AddressType`/`HealthPlanType`/`NotificationFrequency`/`UserProfile`/`Relationship`), auto-validated by the framework off the entity's fields; `internal/domain/aggregatevos/` — the **aggregate value objects** `Address` (base-child, shared across roles), `Dependent` (role child carrying the health-plan sibling facet) + `JobHistory` (role child), each validated through its own `BuildRules`.
- `internal/application/` — `commands/` (+ co-located Results + manual `commands/handlers/`), `queries/` (+ manual `queries/handlers/`), `dtos/`, `translations/` (7 catalogs).
- `internal/infra/` — `schema.go` (the explicit `TableSchema` Go↔column map, threaded into both repos + the view), repositories, `views.go`, `external/` (outbound HTTP adapters wrapping `omnicore/infra/httpclient`). Go only.
- `internal/web/` — Fiber routes (`MountXxx` per concern), `requests/` (+ co-located Responses), `responses/`. Owner of wire tags.
- `proto/` — the service-owned protobuf contract (`users/v1/users.proto`, qa `qafixtures/v1/qa.proto`) plus `gen/` (committed generated Go — dependency-free, importable by BOTH `internal/web` and `internal/infra`, which is why it sits outside `internal/web`) and `generate.sh` (the official protoc invocation, incl. the `-I` into the framework checkout for the shared `omnicore/v1/query.proto`). Outside `internal/` on purpose: the contract is the publishable piece another team copies to call this service.
- `bootstrap/` — `package main`: `main.go` (~10 lines), `wire.go`, one `*_feature.go` per feature.
- `migrations/{postgres,mysql,sqlserver,oracle}/` — domain DDL split by dialect; the service's own migrations are an INDEPENDENT sequence starting at `0001` (the framework's embedded `0001_framework` is tracked in a separate table, so there is no collision).
- `devops/` — local bench (`docker-compose.yml`, `debezium/`, `keycloak/`, `elk/`); replaced by real infra in production.
- `qa/` — end-to-end bash suites (see below).
- `microservice.*.yaml` — one file per profile (`dev` + `prd*` auth variants), selected by `APP_PROFILE`; plus two the QA suites point at explicitly via `OMNICORE_CONFIG_PATH`: `microservice.qa.yaml` (dev + the qa integration/upstream wiring) and `microservice.sqlite.yaml` (the SQLite posture — **no `transport:` block at all**).

Import alias convention in files needing both `domain` packages: `domain` = framework, `appdomain` = this service, `fwinfra` = framework infra.

For any framework concept (BaseEntity, Rules DSL, Pipeline, Auto handlers, BaseRepository/ScopedRepository, AggregateLoader, TableSchema, ViewReader, auth/authz, httpclient, cache, integration events, tracing, bootstrap, OpenAPI, GraphQL, migrations), see [`../omnicore/CLAUDE.md`](../omnicore/CLAUDE.md) and its Documentation Map into the HTML manual at `../omnicore/docs/`.

## Example-specific notes

- **Backend-agnostic.** Repos/service/tests take the neutral `core.RelationalEngine` (`Deps.DB`); the SQL backend is chosen by `relational.dialect` in YAML. Only the YAML, `devops/`, and `qa/*.sh` name a concrete backend.
- **Manual showcase** (`/showcase/users-custom/*`) persists the SAME `users`/`addresses` tables as `/users/*`; it exists to make the wrapper internals visible. Identifier is the user's **email** (`path:"email"`), treated as immutable on that surface. Projection still reuses framework infrastructure (`AutoFromDoc`/`RespondPaged`) — "manual" means the orchestration steps, not re-implementing primitives.
- **Authorization** — all three framework layers are exercised: Layer 1 (`fwopenapi.RequirePermission` on routes), Layer 2 (`BuildRules` owner-check in the `r.IfArchive` clause, fields fed by the Command mapper from `ctx.Identity()`), Layer 3 (tenant) wired but not exercised (User has no `tenant_id`).
- **Nullables** — empty JSON input → nil → NULL (`User.Phone`, `Address.Label`/`Complement`); no `db:` tags, the Go↔column map lives in `internal/infra/schema.go`.

## How to run

Two docker benches, deliberately separate so the QA suites never disturb a manual session:

- **Dev bench** — `devops/docker-compose.dev.yml` (project `omnicore-dev`): your exclusive manual/demo env — MySQL + NATS JetStream + Mongo + a Debezium **Server** relay (MySQL → NATS), minimal (no keycloak/redis/jaeger/elk), on the STANDARD host ports.
- **QA bench** — `devops/docker-compose.yml` (project `omnicore-qa`): the automated bench `qa/run.sh` drives, running the four engine×transport lanes in WAVES of two on a COLD BENCH — each wave brings up only its lanes' containers (engine + broker + relay + redis), runs, then stops them, so the parallel lanes never pay for idle neighbors (CDC relays poll continuously even with no traffic). `run.sh` manages the containers itself; the SQL Server and Oracle lanes' services sit behind the compose **profiles `sqlserver`/`oracle`**, and outside a run the base bench stays two-lane (A/B), which `run.sh` restores at the end.

```bash
./run-dev.sh   # brings up the dev bench + runs the service (APP_PROFILE=dev, MySQL + NATS, :8080)
```

Two build tags are **mandatory**: a **relational engine** (`-tags postgres`, `-tags mysql`, `-tags sqlserver`, `-tags oracle`, or a combination — a multi-engine build picks the dialect at boot from `relational.dialect`) AND a **message transport** (`-tags nats` — NATS JetStream, what the dev bench uses; `-tags kafka` — Kafka/Redpanda). So a runnable build is e.g. `-tags 'mysql nats'`; building without a transport tag aborts at boot with "no transport linked". Read side is eventually consistent (outbox → CDC relay → broker → SyncEngine → Mongo, ~100-300ms after a write).

**Dev-bench ports** (standard): app `8080`, gRPC `9090`, mysql `3307`, mongo `27018`, nats `4222` (+ monitor `8222`). The Debezium Server relay has no host port (static config, no REST API). Creds `omnicore`/`omnicore`, db `users_db`.

**QA-bench ports** (SHIFTED so both benches can run at once): the lanes run apps on `8081`/`8082`/`8084`/`8086` (gRPC `9091`/`9092`/`9093`/`9097` — `8083` is taken by lane A's Kafka Connect REST); shared shifted infra mysql `3317`, mongo `27028`, nats `4232`; lane-only infra postgres `5433`, kafka `9094`, Kafka Connect `8083`, redis `6380`/`6381`/`6382`/`6383`, keycloak `8088`, jaeger `16686`; sqlserver-profile-only infra sqlserver `14333`, kafka-sqlserver `9095`, connect-sqlserver `8085`; oracle-profile-only infra oracle `15211`, nats-oracle `4242` (monitor `8242`). The jaeger + ELK containers are optional observability (ELK behind the `elk` profile, off by default); nothing in the data plane depends on them.

## QA suites (`qa/`)

The end-to-end bash+curl suites (see the table), plus the orchestrator **`qa/run.sh`** — the one-command matrix. It runs FOUR engine×transport lanes in **waves of two** (`QA_MAX_PARALLEL_LANES`), each lane mapped 1:1 onto an engine + a transport + a CDC relay, so every leg of the framework is exercised each run — both brokers twice, both relay flavors twice:

- **Lane A** — Postgres + Kafka + Mongo, relay Debezium **Connect** (app :8081, gRPC :9091)
- **Lane B** — MySQL + NATS + Mongo, relay Debezium **Server** (app :8082, gRPC :9092)
- **Lane C** — SQL Server + **dedicated** Kafka + Mongo, relay Debezium **Connect** (app :8084, gRPC :9093). Dedicated broker by design: SyncEngine topic names (`<table>.events`) are a cross-service contract with no suffix knob, so sharing lane A's broker would cross the lanes' event streams. Its `register-connector.sh` arm also enables SQL Server CDC (`sp_cdc_enable_db`/`sp_cdc_enable_table`) before registering the two connectors. The lane runs local by default (compose profile `sqlserver`; the mssql image is amd64-only — Rosetta on ARM) or against a remote docker engine via `QA_SQLSERVER_CONTEXT` + `QA_SQLSERVER_DB_HOST`.
- **Lane D** — Oracle Free 23ai + **dedicated** NATS JetStream + Mongo, relay Debezium **Server** (app :8086, gRPC :9097). Dedicated server for the lane-C reason (subject names are the contract); the relay is the lane-B pattern (static config in `devops/debezium/conf-oracle-nats/`) over the OracleConnector (LogMiner — expect a ~2-3s write→doc floor, the mining cadence). Its `register-connector.sh` arm enables per-table supplemental logging and pre-creates the relay's heartbeat stream. Local by default (compose profile `oracle`, ARM64-native image) or remote via `QA_ORACLE_CONTEXT` + `QA_ORACLE_DB_HOST`.

**SQLite is an ISOLATED individual step, NOT a lane.** SQLite has no CDC source (Debezium cannot tail a SQLite file), so Mongo-projected views never materialize on it — its read side is the RELATIONAL view (served straight from the SoR). It therefore cannot run the projection-dependent `*.sh` suites as a lane, and is run apart by `qa/sqlite.sh`: boot the SQLite engine as the SoR (pure-Go `-tags 'sqlite nats'`, `CGO_ENABLED=0`) through **`microservice.sqlite.yaml`, which declares NO `transport:` block** — SQLite cannot be a CDC source, so the only events its SyncEngine could ever receive on `<table>.events` (a cross-service subject name, not a per-lane one) are ANOTHER service's, which it would faithfully project into its own Mongo; unsubscribed, the Mongo-backed views stay empty BY CONSTRUCTION, which is what §17 asserts. Mongo itself stays attached only because `/persons` is a `SharedBaseView`, a shape `RelationalSource` cannot serve. It then asserts the WRITE side end to end over real HTTP (aggregate write, SharedBase reuse across roles, soft-delete cascade, hard delete + savepoint purge-veto, probes, migrations), each verified directly against the `app.db` file with `sqlite3`. `./qa/run.sh sqlite` runs ONLY this step (no lanes, no bench waves — it `exec`s `sqlite.sh` before the lane machinery); `./qa/run.sh` runs the four DB lanes THEN this step at the end, and a RED SQLite step turns the whole run RED. Its domain migrations live in `migrations/sqlite/`.

**Lane availability**: judged per wave, after the wave's containers start — a lane whose infrastructure does not answer (for lane C: the DB container on its docker context + the local `kafka-sqlserver`; for lane D: the DB + `nats-oracle`) is SKIPPED — its report cells render **⚠ SKIP** (never RED) and the verdict stays green — so `./qa/run.sh all` works on any machine while showing exactly what did not run.

Each lane runs on its OWN app ports, single-transport binary (`-tags 'postgres kafka'` / `'mysql nats'` / `'sqlserver kafka'`), CDC relay, Redis and Mongo DB (`users_views` / `users_views_mysql` / `users_views_sqlserver` / `users_views_oracle`), so a wave's lanes run the whole suite list concurrently without colliding — wall-clock ≈ the sum of the waves' slowest lanes. `qa/run.sh` boots/stops a per-lane server for the "running already" suites, (re)starts each lane's relay via `register-connector.sh` (which dispatches by dialect: Connect REST for postgres and sqlserver — the sqlserver arm enabling CDC first — a Debezium Server recreate for mysql and oracle, the oracle arm enabling supplemental logging first) and proves it streaming, then before any CDC-dependent suite proves the pipeline hot with a sentinel round-trip (outbox → relay → broker → SyncEngine → Mongo; `QA_CDC_DEADLINE` knob, default 90s, exits early when satisfied). **The serial suites (`schema_evolution`, `rebuild_scale`) run at the END of each wave**, one lane at a time (they patch the shared source tree — views/schema/DTOs — and rebuild, so they can never run concurrent with another lane's build), before the wave's containers stop. `rebuild_scale` is heavy (a full-aggregate bulk seed + multi-pod blue-green rebuild), so run.sh pins its per-lane seed to `REBUILD_SCALE_SEED` (default 250001; its own standalone default is 1,000,000). That default sits deliberately ABOVE the suite's `WINDOW_MIN` (250000): below it the dual-apply window check only REPORTS, so the suite can go green without ever exercising the flip window — at/above it the check is a hard assertion. Report: `../qa-report.md` at the stack root, one section per lane, plus a final verdict (exit 0 only when every scheduled run is green or ⚠ SKIP; an ABORT row or a never-ran suite turns it red). **Fail-fast by default**: the first RED suite on any lane trips a shared sentinel and every lane stops at its next boundary. There is NO way to disable it: `--keep-going` and `KEEP_GOING=1` both abort the run before anything starts. `./qa/run.sh postgres|mysql|sqlserver|oracle` limits to one lane; `SUITES="e2e employee" ./qa/run.sh` limits the suites. Prereqs: Docker + `jq` — `run.sh` manages the bench containers itself (shared trio up front, lane groups per wave, lanes A/B restored at the end). **Lane-driven**: every script sources `qa/_backend.sh`, which maps `BACKEND=postgres|mysql|sqlserver|oracle` onto the whole lane (engine, transport, ports, relay, containers, per-lane Redis + Jaeger service name, plus lane SQL fragments like `$QA_SQL_TOP1`/`$QA_SQL_TRUE` where the dialects diverge). **A green run means EVERY lane green — the engines diverge on dialect specifics (placeholder `$n` vs `?` vs `@pN`, UUID codec, TOP vs LIMIT) and the transports on delivery mechanics, so one lane green does not imply another.** Per rule #2, expectations are an oracle — don't edit them to mask a regression.

"Self-managed" scripts build + start + stop the server themselves; the "running already" scripts (`e2e`, `employee`, `person`, `httpclient`, `openapi`, `graphql`) need the lane's service started first (`qa/run.sh` does this automatically). To run one by hand, source the lane env and boot that lane's single-transport binary — e.g. lane B: `export BACKEND=mysql; source qa/_backend.sh; go build -tags 'mysql nats' -o /tmp/srv ./bootstrap; APP_PROFILE=dev /tmp/srv` (the sourced env sets the dialect, transport endpoints, ports and `$BASE` the suite reads).

**The qa-only mirror suites** (`lifecycle_hooks`, `filter_operators`, `aggregates`, `view_options`, `status_mapping`, `probes`, `http_hardening`, `httpclient_middleware`, `upstream_composition`, `composed_view`, `external_embed`, `link_in_child`, `view_embed`, `composite_vo`, `integration_events`, `transport`) build their OWN `-tags '<engine> qa'` binary and boot `microservice.qa.yaml` (= dev.yaml + the qa integration/upstream wiring) via `OMNICORE_CONFIG_PATH`. Most exercise the **qa-only `Gadget` mirror aggregate** (`//go:build qa`, under the `*/qafixtures/` subpackages) — the framework features the canonical User/Employee example does not: lifecycle hooks, the full filter-operator vocabulary, DeleteOnArchive/MaxLimit/RawDoc view options, the 413/500/503 status mappings, the advanced httpclient middleware, and the integration-events / upstream-composition subsystems. `aggregates` adds the `Product` fixture (`qa_products`) — the write-path aggregate-DSL consumer: a stats endpoint over `Aggregate`/`AggregateBy` and a BuildRules invariant fed by grouped facts through a `domain.Service` port. `external_embed` adds a second qa fixture family — the `Item` embed source plus the `AccountHolder` shared-base role (`qa_accounts`) and the `Catalog` normal aggregate (`qa_catalogs`) — to prove external `Embed`/`EmbedMany` compose and recompose on BOTH a `SharedBaseView` and a regular `query.View`. `auth_selfissued` adds a THIRD kind of qa fixture — not an aggregate at all: `AuthFeature` (mount-only, no domain) plus a self-provisioned `qa_refresh_tokens` table back `web/authcore.Issuer`'s `RefreshTokenStore`/`TokenChecker` seams, proving the framework's self-issuance capability against a real database and a real Redis without touching the canonical User/Employee example. `composite_vo` adds the `Contract` fixture (`qa_contracts`) — the composite-value-object consumer, declared with BOTH read backings over one root so decomposition is proven on the Mongo projection and on the relational twin alike. All of it is invisible to the canonical binary (`go build ./bootstrap` never compiles it), so a reader of the reference service is never confused by QA scaffolding.
